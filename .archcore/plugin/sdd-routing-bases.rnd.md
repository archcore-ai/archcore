## Goal

Ground the redesign of the sdd track's routing in field evidence: determine which bases AI-SDD tools and engineering organizations use to decide which documents a piece of work receives, and validate a candidate routing model against a corpus of real tasks.

## Questions

1. Which routing bases decide document ceremony in AI-SDD tools and in documentation practice at engineering organizations?
2. Does a single axis — work size or work type — cover the task spectrum?
3. Which bases exist beyond input classification, and which fit a living-canon system?
4. How does the candidate model behave on real tasks from this repository and other stacks?
5. Which enforcement and lifecycle constraints does field evidence impose on a routing redesign?

## Approach

Seven parallel research passes on 2026-08-15 over primary sources — repositories, command templates, validator sources, issue trackers, arXiv — covering 28 tools, six organizational documentation practices, and requirements-engineering literature. All URLs cited below were fetched 2026-08-15. Internal grounding against this corpus and the track files under @plugin/plugins/archcore/skills/_shared/tracks/. Validation: a 40-task routing bench — 14 issues and commits of archcore-ai/plugin plus 26 cross-domain tasks — traced through the candidate model.

## Findings

1. No surveyed tool in active use runs one fixed-depth cascade for every work item. Kiro ships two shapes plus a gate-free tier (https://kiro.dev/docs/specs/quick-spec/); BMAD v6 ships three scale tracks with escalation (https://github.com/bmad-code-org/BMAD-METHOD); OpenSpec ships delta-based changes with a lite/full risk split and `skip_specs` for zero-delta work (https://github.com/Fission-AI/OpenSpec); cc-sdd v3 routes through five documentation-delta discovery paths (https://github.com/gotalab/cc-sdd). The market equilibrium is 1–2 shapes × 2–3 tiers; AI-DLC's nine scopes with near-zero community adoption mark the over-segmentation bound (https://github.com/awslabs/aidlc-workflows).
2. Vendors retreated from fixed cascades under measured ceremony cost: Kiro added Quick Spec because users defaulted to vibe mode (https://kiro.dev/docs/specs/best-practices/); Agent OS v3 retired its spec and task phases to host plan modes (https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md); GitHub sunset Copilot Workspace after adding spec-skip and plan+implement (https://gist.github.com/idan/15f101b8ff4be8bebe17147c08995363); Spec Kit's leading complaint is ceremony on small changes (https://github.com/github/spec-kit/issues/1174). Measured overhead on one rebuilt feature: 33.5 min agent time plus 2,577 lines of generated markdown versus 8 min iterative (https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html).
3. Size alone fails as a routing axis: document need varies on dimensions size does not track — contract exposure, reversibility, compliance (OpenSpec full-spec triggers; Amazon one-way/two-way doors). Organizations route by ambiguity (https://www.industrialempathy.com/posts/design-docs-at-google/), blast radius ("substantial", https://github.com/rust-lang/rfcs/blob/master/text/0002-rfc-process.md), cost asymmetry (https://works.hashicorp.com/articles/writing-practices-and-culture), and fixed appetite (https://basecamp.com/shapeup/1.1-chapter-02); document weight scales inside a type, and problem-to-solution cascades are exception paths for large or novel work. Cockburn established methodology weight as team size × criticality (IEEE Software 17(4), 2000, https://dl.acm.org/doi/10.1109/52.854070); ISO/IEC/IEEE 29148 defines tailored conformance.
4. Work-type shapes alone also fail: variance inside the feature shape still demands a depth dial, and each added shape adds a misroutable boundary. Scale is measured only after decomposition — cc-sdd escalates on 20+ generated tasks, BMAD on detected scope creep — so size serves as an escalation trigger, not an entry guess.
5. Delta-against-canon is the one basis that classifies work by its output: which canon documents the work creates, modifies, or leaves untouched (OpenSpec capability deltas; cc-sdd discovery paths). Under it a bugfix is a modifies-case resolved by a code-wrong/spec-wrong verdict, a refactor is a zero-capability delta, and multi-spec decomposition is creates ≥ 2 (Kiro guidance: one spec per feature, never one per codebase, https://kiro.dev/docs/specs/best-practices/). The basis is available only to systems holding a living canon — per-feature-artifact tools cannot diff against documents that die at merge.
6. A supply-side basis is independent of the delta: ceremony tracks the information gap, not task complexity. The greenfield/brownfield split is BMAD's largest branch; AI-DLC runs reverse engineering only on existing code; Spec Kit's `[NEEDS CLARIFICATION]` markers and clarify taxonomy scan measure completeness; the dominant brownfield agent failure is missed existing context (https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html). Five source classes cover the gap: machine-reachable (code, canon, git), the user, external sources, undecided, and empirical-only.
7. A maturity basis ships in the field: MoAI-ADK's `lifecycle: spec-anchored | spec-lite | exploratory` frontmatter (https://github.com/modu-ai/moai-adk); the spec-first / spec-anchored / spec-as-source ladder (https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); ByteRover's statistical maturity tiers (https://arxiv.org/abs/2604.01599). Strictness attaches to the touched zone, not to the work item.
8. Bench results over 40 tasks: about 30% resolve to a null route (no document licensed). The model reproduces this repository's recorded flows — the Copilot adapter shipped as adr → spec → plan (archcore-ai/plugin#24), the Codex adapter as rnd → adr/spec → plan, and the model derives the same rnd + spec + plan route for the OpenCode adapter (archcore-ai/plugin#25). Weak points surfaced: capability granularity is undetermined without a written policy; empirical-dominant tasks need a spike outcome; NFR-dependent routes vary with canon completeness.
9. Enforcement and lifecycle constraints: prompt-only process rules leak in every surveyed tool — LLM-invented status values (gotalab/cc-sdd#162), systematically skipped logging (Pimzino/spec-workflow-mcp#199), state split-brain (Priivacy-ai/spec-kitty#3323); plain-git shared state failed at multi-agent scale and forced a storage migration (https://steve-yegge.medium.com/beads-blows-up-a0a61bb889b4). Post-implementation artifact afterlife splits three ways: delete (BMAD), archive-after-merge (OpenSpec), keep-everything (Spec Kit, Kiro — with documented drift). Prompt-specificity payoff is task-dependent and concentrates in I/O contracts, edge cases, and step breakdown (https://arxiv.org/abs/2508.03678); oversized planning context degrades the executing model (https://research.trychroma.com/context-rot).
10. The full bases catalog splits into two families. Diff-referenced bases: the capability canon (adopted); the decision canon — the unit of documentation is the decision, not the project (https://works.hashicorp.com/articles/writing-practices-and-culture), and it complements the capability delta because a refactor carries a zero capability delta with a non-zero decision delta; executable behavior — tests as canon, the one basis with mechanical drift detection (Tessl integrity model, https://docs.tessl.io/), set aside as a system basis because adr, rule, and guide content does not reduce to tests; the retroactive code delta — the capture cluster, set aside as a sole basis because a diff records no rejected alternatives, and already present as the review-side half of the loop. Non-diff bases: the uncertainty inventory (Spec Kit clarification markers; Superpowers spike/bounded/architectural triage, https://github.com/obra/superpowers); risk exposure; fixed appetite; zone maturity; execution distance — ceremony scales with context discontinuity, dormant until plans execute autonomously; deviation-from-convention, already embedded through global sources.
11. Combination analysis over the bench: no single basis survives it. The capability delta alone loses the refactor's decision record; maturity alone and uncertainty alone leave the output structure — how many specs — undetermined; size alone projects a vector of needs onto a scalar. The surviving composite reads as demand (capability plus decision delta), supply (gap profile), seriousness (zone maturity), and insurance (risk flags); every surveyed live tool is a two-to-three-axis composite, and none runs all four.

## Recommendation

Adopt a computed routing model for sdd with four inputs: canon delta as demand (which documents the work licenses), gap profile as supply (how each document gets filled — compose, interview, research, decide, or spike), touched-zone maturity as strictness, and a five-flag risk list as escalators. Present S/M/L/XL as labels of the computed route, never as user choices. Phase the rollout — delta first, gap profile second, maturity and risk third — and convert the 40-task bench into routing regression scenarios.
